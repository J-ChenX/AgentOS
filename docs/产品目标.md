# AgentOS 产品目标

> 本文档是 AgentOS 的产品形态纲领，所有功能设计、架构决策、路线图优先级均应以此为依据校验。

---

## 一句话定位

**AgentOS 是面向 Python 开发者的开源通用 Agent 编排框架：Skills 即插件，前端面板即插件，LLM 负责意图识别与任务调度，Skills 负责确定性的渲染契约——比 Dify 更 code-friendly，比 LangChain 更开箱即用，并致力于定义开放的 Agent-UI 通信协议标准。**

---

## 产品愿景

任何开发者只需要：

1. 编写 Python `@tool` 函数（Skills）
2. 在 `agent.toml` 中声明引用
3. 运行 `agentos run`

就能得到一个完整可用的、对话驱动的 AI Agent 产品，并通过 Web UI 提供给最终用户使用。

**Skills 赋予 Agent 能力，Agent 负责理解任务并调度 Skills，前端面板负责将结果以最合适的形式呈现。**

---

## 核心架构哲学

### 三层分离

```
能力层  Skills         → 纯 Python @tool 函数，只管数据和逻辑，可携带渲染契约
编排层  Agent Runner   → LLM 驱动，负责意图识别 + 参数提取 + Skill 调度（不独立决策 UI）
展示层  前端面板系统   → 插件化面板，优先执行 Skill 渲染契约，其次响应 LLM 提示，支持用户手动切换
```

### 展示决策：双轨机制（强提示 + 弱提示）

UI 渲染需要确定性，LLM 是概率模型。两者不能混用在同一层——这是核心架构约束：

| 轨道 | 触发方式 | 优先级 | 适用场景 |
|------|---------|--------|---------|
| **强提示（Skill 决定）** | Skill 返回带类型标注的数据对象，如 `ChartData(...)` / `ImageResult(...)` | **高** | Skill 明确知道输出类型（图表、图片、表单） |
| **弱提示（LLM 建议）** | LLM 在 SSE 事件中携带 `"panel"` 字段作为建议 | 低（兜底） | Skill 返回通用 dict，LLM 推断展示方式 |
| **用户切换** | 面板顶部手动选择 | 覆盖一切 | 用户对展示方式有主观偏好 |

**LLM 只负责意图识别和参数提取，不单独决策 UI 渲染。** 渲染契约应尽量由 Skill 的返回类型来保障。

### 前端面板是插件

面板类型（Chat / Chart / Table / ImageGallery / Form / Files / Config…）是可扩展的插件注册表，不是硬编码的。未来任何 Skill 都可以随包带一个新面板类型，框架负责注册和渲染。

## 目标用户

### v0.1 阶段（当前）：单一核心用户

**全栈 AI 骇客**——懂 Python、对 LLM 有兴趣、想快速构建并发布一个有 Web UI 的业务 Agent 的独立开发者或小团队。

他们同时扮演"写 Skill"和"搭 Agent"两个角色。对他们的核心承诺是：

> 一个 Python 文件 + 一个 TOML，搞定全端 Agent。

文档、示例、传播都围绕这个单一用户群体设计，不要在 v0.1 阶段拆分角色。

### 未来阶段（生态成熟后）：分层用户

| 用户 | 描述 | 进入时机 |
|------|------|---------|
| **Skill 开发者** | 专门编写 Skills 并发布到 Registry 的开发者 | Skill 生态有一定规模后 |
| **Agent 搭建者** | 通过修改 `agent.toml` 组合现有 Skills 的产品型用户（可不懂 Python）| Skill Registry 上线后 |
| **最终用户** | 业务人员 / 非技术用户 | 随 Agent 搭建者的产品部署 |

## 最终产品形态

### 典型使用场景

**场景 A：数据分析 Agent**
- 挂载 `data_loader` + `sql_query` + `chart_generator` Skills
- 用户对话："帮我分析上个月的销售趋势"
- Agent 调用 Skills 获取数据，决定在 Chart 面板展示，自动渲染折线图

**场景 B：图像生成 Agent**
- 挂载 `image_generation` Skill（调用 DALL-E / Stable Diffusion）
- 用户对话："生成一张赛博朋克风格的城市夜景"
- Agent 调用 Skill，决定在 Image Gallery 面板展示，图片即刻显示

**场景 C：质检 Agent**
- 挂载 `image_upload` + `defect_detection` + `report_generator` Skills
- 用户上传图片，Agent 自动调用检测 Skill，在 Table + Image 面板展示检测结果

### 核心体验指标

- **零配置启动**：`agentos init && agentos run`，5 分钟内得到可用 Agent
- **Skill 即插即用**：添加一个 Skill，Agent 立即获得新能力，无需修改框架代码
- **面板自适应**：Agent 能正确选择合适的面板类型展示不同 Skill 的输出
- **安全可审计**：第三方 Git Skill 的权限清晰可见，commit 版本锁定，可审批

## 竞品定位

| 竞品 | 与 AgentOS 的关系 | AgentOS 的差异化 |
|------|----------------|----------------|
| **Dify** | 最直接竞品，功能最完善 | 代码优先（Python Skills vs 可视化节点）；Skill 安全分发；双轨渲染契约机制 |
| **LangChain + 自定义 UI** | 开发者的常规替代路径 | 消除大量胶水代码，内置 UI + Workspace + 安全模型 |
| **AutoGen / CrewAI** | 多 Agent 编排框架 | 有完整 Web UI，更面向产品化交付 |
| **Streamlit / Gradio** | Python 快速 UI 工具 | 有 LLM 编排层，不需要为每个功能单独写 UI |
| **Claude Code / Codex** | 自主编程 Agent | 不同赛道：开发者工具 vs 业务 Agent 框架 |
| **Devin** | 自主软件工程 Agent | 不同赛道：软件工程自动化 vs 通用业务 Agent |

### 长期护城河：Agent-UI 通信协议标准

2026 年 UI 已不是壁垒，所有工具都在卷界面。AgentOS 的真正护城河是**定义 Agent 与前端之间通信的开放标准**。

当前 SSE 事件格式（`{"type": "component", "panel": "chart", "data": {...}}`）不仅是技术实现，更是一个可被其他客户端消费的协议。如果未来飞书 / 企业微信 / Slack / VS Code 插件都能解析这段协议并渲染对应组件，AgentOS 将从一个框架变成一个生态标准。

**行动方向：**
- 将 SSE 协议文档化并公开（非私有实现）
- 提供多端 SDK（JS / Python client）消费同一 SSE 流
- 最终目标：AgentOS 成为"AI Agent 输出展示层"的事实标准，而不只是一个框架

## 路线图指导原则

### 优先级一：MVP 必须完成（这三项是杀手级 Demo 的前提）

1. **Skill 渲染契约系统**（强提示机制，解决 LLM 不可靠性问题）
   - Skill 返回带类型标注的数据对象时，框架自动拦截并触发对应面板，无需 LLM 判断
   - 示例：`return ChartData(data=df)` → 框架强制触发 `chart` 面板
   - 内置数据类型：`ChartData` / `ImageResult` / `TableData` / `FormSpec` / `TextResult`
   - LLM 的 `panel` 建议仅作为兜底（Skill 未声明类型时生效）
   - 协议细节在独立技术设计文档中定义

2. **Workspace 共享状态机制**（解决大数据跨 Skill 传递问题）
   - Skills 之间不得通过 LLM 上下文传递大体积数据（Token 溢出 + 账单风险）
   - MVP 实现：基于本地临时目录的 Workspace，Skill 可读写文件引用
   - 示例：Skill A 返回 `{"file_ref": "workspace/data.csv"}`，Skill B 接收引用进行处理
   - 这是"数据分析 Agent"场景（50MB CSV）能真正跑通的基础设施
   - 未来扩展：内存 Dict / 远程 KV store（当前只做文件引用）

3. **面板渲染机制完整闭环**（SSE 协议 + 前端动态渲染）
   - Agent 在 SSE 事件中携带展示信息，事件格式：
     ```json
     { "type": "component", "panel": "chart", "data": { ... }, "seq": 5 }
     ```
   - `panel` 字段对应前端 WidgetRegistry 注册的面板类型
   - 前端根据 Skill 渲染契约（优先）或 LLM 建议（兜底）激活面板
   - 用户可手动切换面板类型（覆盖一切）

4. **Skill 杀手级 Demo**（验证以上三项联动）
   - 场景：添加图像生成 Skill → 对话 → 图片出现在 Image Gallery 面板，全程 < 5 分钟配置
   - 场景：数据分析 Skill 拉 CSV → 通过 Workspace 传给图表 Skill → Chart 面板渲染
   - 这是最有力的差异化证明，也是对外传播的核心素材

### 优先级二：产品完整性

5. **持久化会话与任务历史**（长期 Agent 需要记忆）
6. **面板间联动**（一个面板的操作触发另一个面板更新）
7. **Skill 生态基础设施**
   - Skill 模板：一行命令创建符合规范的 Skill 仓库结构
   - Skill 目录 / 可发现性（类似 npm registry，等生态有一定规模再做）

### 优先级三：生态与商业化（未来）

7. 公开 Skill Registry
8. 多租户 / 权限管理（企业部署）
9. Skill 组合市场（预打包的 Agent 模板）

## 不该做的事（避免重复造轮子）

| 不做什么 | 理由 |
|---------|------|
| 自建 RAG / 向量数据库 | 用 LlamaIndex / Chroma 等作为 Skill，不是框架内置 |
| 可视化流程编辑器 | Dify 已赢得该市场，AgentOS 的优势在代码优先 |
| 自建用户认证 / SSO | 用 Nginx / 反向代理方案，不自己实现 |
| 自建 LLM 路由 | 已正确使用 LiteLLM，不重复造轮子 |
| 多 Agent 复杂编排（短期）| AutoGen 已有成熟方案，单 Agent + 丰富 Skills 先做深 |

## 架构红线

> 以下原则在任何功能开发中不得违反：

1. **LLM 不单独决策 UI 渲染**：LLM 只负责意图识别和参数提取；渲染契约由 Skill 返回类型决定，LLM 的 `panel` 建议仅作兜底
2. **大数据不走 LLM 上下文**：超过合理 Token 量的数据（文件、数组等）必须通过 Workspace 文件引用传递，禁止序列化进 prompt
3. **Skills 不感知前端**：`@tool` 函数只返回数据对象（可带类型标注），不直接操作 UI
4. **LLM 只做调度，不做数据变换**：数据处理逻辑在 Skills 里，不在 prompt 里
5. **agent.toml 是唯一真相来源**：运行时只加载声明过的 Skills，不动态发现
6. **第三方 Skills 必须经过审批**：Git 来源的 Skill 必须锁定 commit hash + 权限可见
7. **框架不绑定业务逻辑**：AgentOS 是通用框架，业务逻辑只能通过 Skills 引入
